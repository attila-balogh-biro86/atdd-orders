the problem

AI made code cheap. Verification is the new bottleneck.

A coding agent writes a feature in minutes. But who decides what "correct" means, and who proves the agent delivered it?

01 / ambiguity

Prose is open to interpretation

"Loyalty members get 15% on large orders." Is 1000.00 large? Does it stack with 10%? The agent picks an answer silently.

02 / self-grading

The agent marks its own homework

The same model writes the code and the tests. If it misunderstood the rule, its tests share the misunderstanding.

03 / gaming

Green at any cost

Under pressure to pass, agents edit assertions, skip tests or hardcode the example values. The build is green, the feature is not.

04 / drift

Docs and code drift apart

Requirements in Jira or markdown are not checked against the running system. After three sprints nobody trusts them.

05 / review overload

Humans drown in diffs

Reviewing 2,000 generated lines line by line doesn't scale. Reviewers need evidence, not more code to read.

06 / "done"

"Works on my machine"

Passing locally says nothing about staging or production. "Done" has to be proven in every environment.

spec-driven development

The spec is the source of truth. Code is a derived artifact.

When an agent writes the code, the scarce human work moves upstream to deciding behaviour and downstream to proving it.

A spec-driven workflow writes the intent down first, in a structured form, before any code. The agent plans and implements against it, and the spec outlives each change.

intent before codereviewable artifactversioned with the codeagent-readable

Spec-first

Write a spec, let the agent build from it. The spec is often discarded after the task.

Spec-anchored

The spec is kept and evolved with the feature, and each change starts from a spec change.

Spec-as-gate (this talk)

The spec is executable. It fails until the behaviour exists, it gates every PR and it runs against production.

🤖 Claude agents (.claude/agents)

spec-author
Turns the issue into Gherkin rules + examples through example mapping. Asks questions instead of guessing (needs-clarification).
acceptance-engineer
Adds step glue, DSL verbs and driver methods, then proves the new scenarios are red for the right reason.
implementer
Writes production code and unit/property tests until the spec is green. It cannot touch the spec.
spec-conformance-reviewer
Independent, read-only. Did the code implement the rule, or just the example numbers?

lessons from real runs

  
Things that actually happened

  

    
agent "succeeds" in ~20 s, no PR
Silent permission denials

      
In CI, tool calls the agent isn't allowed to make are denied quietly. Check permission_denials_count.

      
→ keep --allowedTools complete

    
changed agents.yml, same behaviour
"Re-run" replays old config

      
Re-running a workflow uses the original commit's YAML. Your fix isn't in that run.

      
→ start a fresh run (re-add the label)

    
reviewer: "non-human actor"
Bots reviewing bots

      
The conformance reviewer refused PRs opened by the Claude bot. Agent-to-agent hand-offs need explicit trust.

      
→ allowed_bots: 'claude'

    
k6: many 404s, normal latency
"Healthy" was the old revision

      
The deploy reported healthy while the old revision still answered. In-memory state was lost on the traffic switch.

      
→ wait until /actuator/info reports the new SHA

    
property test failed after a rule change
Tests pin old rules (good!)

      
discountNeverExceedsTenPercent encoded the old 10% rule. When the rule changes, the tests pinning it must change too.

      
→ a feature, not a bug

    
hardcode-shaped risk
Example ≠ rule

      
Agents love example values. Holdout scenarios with values the agent never sees, plus an independent reviewer, catch "if total == 1000.01".

      
→ implement the Rule: line, not the table

  







  
  

    
    
  

  
takeaways

  
Let agents write the code.
Keep humans in charge of "correct".

  

    
Specs as examples, not prose. Boundaries and rounding are where AI guesses.

    
Make the spec executable, red before code and green after.

    
Separate the roles: who writes the spec is not who satisfies it.

    
Defence in depth: hook, path guard, holdout, mutation and an independent reviewer.

    
One spec, every environment: laptop, preview, staging and production.

    
Markdown SDD and ATDD combine well: plan in prose, gate on examples.
